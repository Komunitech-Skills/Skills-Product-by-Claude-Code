# Peta Dampak Perubahan — WAJIB dibaca sebelum menawarkan perbaikan apa pun

Setiap perbaikan yang ditawarkan skill ini **wajib** menyertakan baris "**Efek yang berhenti
bekerja**" (lihat Format Output di `SKILL.md`). Tabel ini adalah sumber kebenarannya — semua
baris **diverifikasi langsung** di OpenClaw 2026.9.5 (mesin uji terisolasi) atau dari docs resmi
`docs.openclaw.ai` yang dikutip apa adanya.

| Perubahan | Apa yang BERHENTI bekerja | Kapan aman dilakukan |
|---|---|---|
| **Dua kunci grup WA yang SERING TERTUKAR** — `channels.<kanal>.groups` vs `channels.<kanal>.groupPolicy`/`groupAllowFrom` | Ini **BUKAN satu pengaturan**, jadi salah satunya saja tidak cukup: (1) **`channels.<kanal>.groups`** = daftar **GRUP mana** yang boleh diproses (map berisi ID grup `...@g.us`; kalau `groups` tidak diisi sama sekali, **semua grup** dianggap eligible; isi `"*"` juga berarti semua grup). (2) **`channels.<kanal>.groupPolicy` + `groupAllowFrom`** = daftar **PENGIRIM** (nomor E.164) yang boleh memicu bot **di dalam** grup yang sudah eligible — `open` melewati pengecekan pengirim, `allowlist` mewajibkan `groupAllowFrom` (atau `"*"`) cocok, `disabled` memblokir semua pesan grup. **Peringatan fallback (penting):** kalau `groupAllowFrom` **tidak diisi sama sekali**, pengecekan pengirim **jatuh ke `allowFrom`** (daftar DM). Karena `dmPolicy: "open"` **mewajibkan** `allowFrom` berisi `"*"`, kombinasi ini membuat `groupPolicy: "allowlist"` **tidak membatasi siapa pun** — walau temuan grup sudah hilang dari `security audit`, ini rasa aman palsu. | Kapan aman: **isi `groupAllowFrom` secara eksplisit** dengan nomor yang memang boleh memicu bot di grup — JANGAN memasukkan ID grup ke `groupAllowFrom` (itu salah kunci). Kalau sebelumnya `dmPolicy` juga `"open"` dengan `allowFrom: ["*"]`, **bersihkan dulu `allowFrom`** dari `"*"` (lihat baris di bawah) sebagai bagian dari perubahan yang sama, supaya fallback tidak diam-diam menetralkan `groupAllowFrom`. Kalau ingin membatasi grup mana yang eligible (bukan cuma pengirimnya), isi `channels.<kanal>.groups` dengan ID grup yang ingin dipertahankan; biarkan tidak diisi/`"*"` kalau semua grup yang sudah ada tetap boleh diproses. |
| `channels.<kanal>.dmPolicy`: `open` → `pairing`/`allowlist` | Pelanggan/pasien **baru** (belum pernah chat/pairing/masuk allowlist) **tidak akan dilayani** sampai disetujui manual atau ditambahkan ke `allowFrom`. Untuk `pairing`, kode persetujuan berlaku terbatas (±1 jam) dan **permintaan pairing yang menunggu dibatasi maks. 3 per akun kanal** — permintaan ke-4 dan seterusnya diabaikan sampai salah satu disetujui/kedaluwarsa. **Kalau sebelumnya `dmPolicy: "open"`, `allowFrom` pasti berisi `"*"`** (syarat wajib untuk `open`) — mengubah `dmPolicy` saja TANPA membersihkan `"*"` dari `allowFrom` membuat pengaturan jadi tidak konsisten (dan bisa menetralkan pengetatan `groupAllowFrom`, lihat baris di atas). | Aman untuk kanal notifikasi pribadi (hanya pemilik yang chat). Untuk kanal yang dipakai pelanggan umum, jelaskan dulu bahwa proses onboarding pelanggan baru jadi butuh langkah tambahan, dan **ubah `dmPolicy` BERSAMAAN dengan mengganti `allowFrom` dari `["*"]` ke nomor pemilik/tim** dalam satu paket persetujuan — jangan cuma salah satu. |
| `tools.exec.mode` → `ask` (atau `allowlist`/`deny`) | **Automation/cron yang menjalankan script (dari `laporan-otomatis-terjadwal`, `buku-stok`, dll.) akan DITOLAK OTOMATIS**, bukan menunggu persetujuan — dari dokumentasi resmi (`docs.openclaw.ai/tools/exec-approvals`): *"chat channels never receive automation approvals... With no approval surface connected, the request is denied immediately."* Kalau pengguna tidak membuka Control UI/app untuk menyetujui tiap kali, laporan terjadwal berhenti total. | Aman kalau pengguna **tidak** memakai automation/cron ber-script, ATAU pengguna berjanji membuka Control UI/app tiap kali automation jalan (tidak realistis untuk laporan harian tanpa pengawasan). Kalau pengguna memakai `laporan-otomatis-terjadwal`/`buku-stok`, **peringatkan eksplisit** sebelum mengubah ini. |
| `tools.profile` → `messaging` (sering muncul sebagai remediasi bawaan dari `security audit`) | Profil `messaging` **hanya** berisi tool pesan & sesi (`message`, `sessions*`, `ask_user`, `gateway` mode update-saja) — **TIDAK** ada `exec`, `read`, `write`, `edit`, `process`, `browser` (terverifikasi dari docs `gateway/config-tools/tool-policy`). Artinya **SEMUA skill ber-script Komunitech berhenti berfungsi** (rekap-penjualan-csv, hitung-hpp, buku-stok, dsb. — apa pun yang menjalankan `python3 .../scripts/*.py` atau membaca/menulis file). | **Jangan tawarkan ini sebagai perbaikan default.** Hanya cocok untuk agent yang memang khusus untuk chat/CS tanpa perlu skill ber-script (mis. agent CS terpisah). Kalau pengguna memakai skill ber-script di agent yang sama, jelaskan trade-off ini dengan tegas sebelum menawarkan. |
| `agents.defaults.sandbox.mode` → `all` | AI berjalan di kotak pasir (container) untuk **setiap** sesi. **Butuh Docker (atau Podman) terpasang & berjalan** di komputer pengguna (dari docs `gateway/sandboxing`: backend sandbox berbasis Docker/Podman). Tanpa Docker, agent bisa gagal jalan sama sekali. | Hanya tawarkan setelah menanyakan apakah Docker Desktop/Podman sudah terpasang. Kalau pengguna awam dan belum punya Docker, ini **bukan** perbaikan "satu klik" — jelaskan sebagai langkah lanjutan yang butuh instalasi tambahan, jangan jalankan `config set` begitu saja. |
| `gateway.auth.mode` (mis. `none` → `token`) | OpenClaw sendiri memberi peringatan: **"Restart the gateway to apply."** — perubahan tidak aktif sampai Gateway di-restart, dan klien (Control UI/app) butuh token baru untuk tetap bisa login. **Hanya mengubah `gateway.auth.mode` ke `token` TANPA token asli tidak memperbaiki apa pun** — `security audit` tetap menandai `critical` (`gateway.loopback_no_auth`) sampai ada token nyata. | Jangan set `gateway.auth.mode` manual sendirian — pakai `openclaw doctor --generate-gateway-token` (terverifikasi: membuat token asli sekaligus mengatur `gateway.auth.mode: "token"`, dan mencadangkan config lama). Jelaskan langkah restart & di mana menyalin token baru **sebelum** menjalankan. Untuk pengguna yang sangat awam, sarankan ini dilakukan bersama jasa setup/pendampingan. |
| `openclaw security audit --fix` | **Bukan hanya** merapikan izin file. Terbukti di mesin uji: `--fix` juga **mengubah nilai config secara langsung**, contoh terverifikasi: `channels.<kanal>.groupPolicy` dari `open` menjadi `allowlist` otomatis. Anggap `--fix` sebagai gabungan beberapa perubahan config sekaligus, bukan operasi "aman & netral". | Jelaskan dulu daftar findings yang akan disentuh `--fix` (dari hasil `security audit --json` sebelumnya) sebelum menjalankan, seperti perbaikan config manapun — bukan langsung dijalankan karena "cuma --fix". |

## Cara membaca tabel ini saat memberi rekomendasi
1. Cek dulu **untuk apa** OpenClaw pengguna dipakai (pertanyaan pertama di SKILL.md): pribadi
   saja, dipakai pelanggan/pasien, ikut di grup, dan/atau punya automation/cron berjalan.
2. Untuk tiap temuan 🔴/🟡 yang perbaikannya ada di tabel ini, **salin baris "Kapan aman
   dilakukan"** ke dalam tawaran perbaikan, disesuaikan dengan jawaban pengguna di langkah 1.
3. Kalau perbaikan yang disarankan hasil audit (`remediation`) termasuk `tools.profile:
   "messaging"` atau `agents.defaults.sandbox.mode: "all"`, **jangan tawarkan sebagai default
   satu-klik** — selalu jelaskan efeknya secara eksplisit dan tanyakan dulu apakah pengguna
   memakai skill ber-script / punya Docker.
4. Perubahan yang bisa "mengunci" pengguna dari akses (auth Gateway) sebaiknya dilakukan
   bersama saat pengguna siap, bukan di tengah percakapan santai tentang privasi.
